# План предстоящих работ по фазам

Источник: [task.md](task.md), разделы 8 (модули), 9 (потоки), 13 (API), 14 (Docker), 15 (state machine), 19 (Roadmap), 20 (приемка).

## 0) Подготовка (сквозной старт перед Phase 1)

### Цель
Сформировать базу проекта, чтобы далее реализовывать фазы без переопределения контрактов.

### Работы
- Зафиксировать формат `manifest schema v1` и структуру `content pack` как неизменяемый контракт runtime.
- Зафиксировать идентификаторы и статусы `job` / `pack` (черновой state machine).
- Определить минимальный набор API-маршрутов для Phase 1.
- Подготовить каркас Docker-окружения (`api`, `worker`, вспомогательные зависимости).
- Определить структуру логирования и трассировки (`request_id`, `job_id`, `stage_id`).

### Артефакты
- Документированный контракт `manifest v1`.
- Черновой OpenAPI/endpoint-список для первых фаз.
- `docker-compose` для локальной разработки.
- Базовый каркас репозитория (модули из раздела 8).

### Definition of Done
- Команда может локально поднять окружение и пройти happy-path от запроса до сборки тестового пакета на мок-данных.

---

## 1) Phase 1 - Локальный инженерный прототип

### Цель
Собрать end-to-end пайплайн генерации и сборки `content pack` в локальном Docker-контуре.

### Объем (из ТЗ)
- Python service в Docker.
- API в Docker.
- Worker в Docker (при необходимости).
- ComfyUI локально/отдельно.
- Генерация 4-6 BW кандидатов.
- Нормализация, shortlist.
- Ручной выбор композиции и палитры.
- Palette assignment, segmentation.
- Manifest + assets.
- Импорт в TouchDesigner.

### Задачи реализации
- Реализовать модули:
  - `request_intake`
  - `generation_profile_builder`
  - `candidate_generator`
  - `candidate_normalizer`
  - `candidate_ranker`
  - `composition_selector` (ручной выбор)
  - `palette_selector` (ручной выбор)
  - `palette_assignment`
  - `layer_segmenter`
  - `pack_builder`
  - `validator`
- Реализовать API для:
  - создания job;
  - получения shortlist;
  - фиксации выбранной композиции;
  - фиксации выбранной палитры;
  - сборки и валидации pack.
- Реализовать локальную публикацию в тестовый runtime cache.
- Подготовить smoke/integration тесты для полного потока генерации.

### Артефакты фазы
- Рабочий CLI/API.
- `manifest schema v1`.
- `demo pack`.
- Результат runtime import test в TouchDesigner.

### Definition of Done
- Выполнены приемочные критерии из раздела 20, относящиеся к локальному прототипу.

---

## 2) Phase 2 - Библиотека и publish flow

### Цель
Добавить управляемую библиотеку пакетов и стабильный контур публикации/повторного использования.

### Объем (из ТЗ)
- `library storage`.
- `item statuses`.
- `usage metadata`.
- `publish endpoint`.
- `local runtime cache sync`.
- Начальная curated library.

### Задачи реализации
- Реализовать модули:
  - `library_selector`
  - `publisher`
  - базовую часть `library_promoter` (ручные правила).
- Добавить API для:
  - запросов к библиотеке (фильтры: тема/сложность/цветовые ограничения);
  - публикации пакета;
  - перевода статусов библиотечных элементов.
- Добавить хранение `provenance`, версионности и usage metadata.
- Реализовать политику статусов `pack` (`draft/validated/published/failed`).
- Внедрить синхронизацию `published pack` в локальный runtime cache.

### Артефакты фазы
- Библиотека пакетов с фильтрацией.
- Рабочий publish flow.
- Базовый promotion flow (полуавтомат/ручной контроль).

### Definition of Done
- Пользователь может выбирать pack из библиотеки и получить тот же runtime-совместимый формат, что и для generated-потока.

---

## 3) Phase 3 - Серверный запуск

### Цель
Перенести pipeline из локального режима в серверный multi-job контур.

### Объем (из ТЗ)
- Отдельный сервер для pipeline.
- Object storage.
- Job queue.
- Доставка pack на тестовые столы.
- Стабильные фоновые jobs.
- Переход к серверному контейнерному развертыванию.

### Задачи реализации
- Вынести хранение ассетов/пакетов в object storage.
- Добавить очередь и воркеры для асинхронной обработки.
- Реализовать retry/error policy (раздел 17) без повреждения библиотеки.
- Укрепить state machine job/pack и наблюдаемость (логи + трассировка по `request_id`).
- Добавить runtime delivery для тестовых столов с контролем версий.
- Обновить Docker-контур под серверное разворачивание.

### Артефакты фазы
- Server deployment.
- Multi-job processing.
- Runtime sync.
- Production-ready контейнерный контур backend-части.

### Definition of Done
- Пайплайн стабильно обрабатывает несколько jobs параллельно, с контролируемыми ошибками и воспроизводимыми publish-результатами.

---

## 4) Phase 4 - ComfyUI Cloud / внешние backend'ы

### Цель
Сделать генерацию backend-агностичной без изменения контракта `content pack`.

### Объем (из ТЗ)
- Переключаемые backend'ы.
- ComfyUI Cloud.
- Optional OpenAI / Firefly routes.
- Unified backend adapter layer.

### Задачи реализации
- Спроектировать и внедрить `backend adapter interface`.
- Подключить как минимум 2 backend-провайдера через единый контракт.
- Обеспечить согласованность `provenance` независимо от backend-а.
- Добавить конфигурационный выбор backend-а на уровне job/profile.
- Добавить тесты эквивалентности: одинаковые требования профиля -> валидный pack одного формата.

### Артефакты фазы
- Backend abstraction layer.
- Конфигурируемый выбор генератора.
- Подтвержденная консистентность provenance.

### Definition of Done
- Замена генерационного backend-а не требует изменения `manifest schema` и runtime-контракта.

---

## 5) Phase 5 - Аналитика библиотеки и правила promotion

### Цель
Повысить качество curated library за счет метрик использования и полуавтоматических решений.

### Объем (из ТЗ)
- Usage scoring.
- Метрики started/completed.
- Auto-promotion suggestions.
- Content retirement rules.

### Задачи реализации
- Ввести модель метрик по pack и library item.
- Реализовать scoring и ранжирование библиотечных элементов.
- Расширить `library_promoter` правилами автопредложений.
- Добавить retirement-политику для устаревшего/проблемного контента.
- Добавить дашборд/отчетность для продуктовых и контент-решений.

### Артефакты фазы
- Semi-automatic library curation.
- Quality-based ranking.
- Правила вывода контента из активного каталога.

### Definition of Done
- Библиотека поддерживается на основе фактического качества и использования, а не только ручной модерации.

## Сквозные треки (выполняются во всех фазах)

- Тестирование:
  - unit на модули;
  - интеграционные тесты на полный data flow;
  - контрактные тесты `manifest` и runtime-совместимости.
- Наблюдаемость:
  - структурные логи;
  - трассировка по `request_id/job_id`;
  - журнал ошибок по стадиям.
- Качество данных и контента:
  - контроль ограничений по цветам, сложности, геометрии, моторной пригодности;
  - проверки валидатора перед publish.
- DevOps:
  - reproducible Docker build;
  - compose для локальной разработки;
  - серверный контейнерный контур без смены формата pack.

---

## Приоритеты реализации

1. Зафиксировать контракт `content pack` и `manifest v1` до масштабирования фич.
2. Закрыть end-to-end в Phase 1 и проверить импорт в TouchDesigner.
3. Затем развивать библиотеку/публикацию (Phase 2), и только после этого масштабировать инфраструктуру (Phase 3+).
